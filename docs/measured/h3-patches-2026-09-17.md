# H3 speed patches vs the shipped basic — 2026-09-17

WORKPLAN §13c / NEXT UP 1. Local session, overnight loop, owner's machine.

## Question

The shipped basic `AE_LLAMA_H3_T2V_V1` is core-only (§22a). The owner's
authored H3 graph also carries three pack nodes. What does dropping them
cost, in seconds, in peak VRAM, and in the picture?

## Setup

- RTX 5090 (32 607 MiB), managed ComfyUI 0.34.0, python 3.13.14,
  torch 2.13.0+cu130, shipped boot flags `--disable-pinned-memory
  --use-ck-attention`, whole card, AE open.
- `node scripts/catalog-vram-probe.js --entry minimax-h3` for every arm
  (seed 12345, 1344x768, 124 frames / 5.17 s, 20 steps, the probe's
  standard prompt). Variant graphs came from `--workflows-dir` (added for
  this), so nothing under `extension/` changed.
- Arm A ran on the managed interpreter with no packs. Arms B-D ran on a
  COPY of it (`python_h3c`, deleted afterwards) with
  `triton-windows 3.7.1.post27` and the woct0rdho `sageattention 2.2.0
  post6` wheel installed, plus kjnodes' pip deps. Packs were copied from the
  owner's `Documents/ComfyUI/custom_nodes` and loaded through an extra
  `--extra-model-paths-config` holding a `custom_nodes:` key. The managed
  interpreter and vendor tree were never modified (checked afterwards:
  no triton, sageattention or matplotlib).
- Patch settings are the authored ones: Sol `tau 2.0 -> 0.8 linear, dense
  20 %, strict, diag`; FirstBlockCache `H3 Safe — 0.08 / max 2`. The chain
  follows the authored order: SigmaShift -> [FBC] -> [Sage] -> [Sol] ->
  BasicGuider. The scheduler stays on SigmaShift, as authored.

## What it says

1. **FirstBlockCache is the whole win: -19 % wall clock (153 -> 124 s),
   and it barely changes the picture** (SSIM 0.978 against the basic). The
   per-step trace shows why: from step 6 to 16 every other step is a cache
   hit (under 1 s instead of 6.35 s), so 5 of 20 transformer passes are
   skipped.
2. **The two attention patches are worth ~4 % (153 -> 147 s) and they
   change the sample.** The Sage patch runs at exactly CK's pace
   (6.35 s/it against 6.44), which agrees with 7b-2 on Wan: on this card,
   CK INT8 attention already gives what Sage gives. Sol switched itself on
   ONLY for the last 4 steps (`[MiniMax H3 Sol] active (37754 tokens)` at
   16/20) and made those ~1.2 s/step faster. Frame 60 of B and C is a
   correct picture of the same scene with slightly different framing
   (`local/h3c-f60-ABC.png`, not committed), so "different", not "broken".
   But it is a different clip, where FBC alone is nearly the same clip.
3. **No arm lowers peak VRAM, so H3's gate of 32 does not move.** Peaks
   read 29.4-31.8 GB across arms, with A and C (no patch / every patch)
   within 4 MiB of each other. The spread is sample-level noise of the
   kind 7d/7e found: 7c published this same basic at a 28 705 MiB peak.
   `MemoryEfficient` in the Sage patch's name buys nothing measurable here.
4. **Install cost is lopsided.** FBC is 338 lines of pure Python (torch +
   comfy imports only), MIT (duckyshell). Sol needs Triton, and the Sage
   patch needs the sageattention wheel. Found on the first B run: Triton's
   JIT **fails on the portable embedded interpreter** because it has no
   `Include/Python.h` or `libs/python313.lib` (tcc: `cpython/pymem.h` not
   found). It works once the matching headers and libs are added from the
   official `python` 3.13.14 NuGet package. Any §22d install of sol-attn
   has to carry that step.

## Not measured

- n = 1 per arm. The seconds are sampling-dominated and step times were
  stable to 0.01 s/it, so the ranking is safe. The peaks are not.
- Small cards. FBC skips compute, not weights, so it should not change a
  gate, but that is reasoning.
- `H3 Fast` / `Aggressive` cache modes, and fidelity at other prompts or
  lengths.
- i2v (the fixture is i2v; the basic that ships is t2v).
